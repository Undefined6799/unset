# Paired PDS frontend build

`source.lock.json` fixes the official PDS image, Node builder, upstream source archive and lockfile. Its `linux/amd64` platform is the native CI target. The exact schema, Dockerfile interface and clean-checkout verifier command are in [the checker contract](../../scripts/ci/pds-ui/README.md); updating any source or package version requires reviewing that contract with this recipe.

The source is `bluesky-social/atproto` revision `fb16c8e0247fb5159fd23ce0e5301249532d1b4e`. Its archive SHA256 is `8ec64f48214236a37ffe739b17fe80bfd060c2cf438ff028484cb24ebcc4dc08`; its `pnpm-lock.yaml` SHA256 is `371a48189e93b5868a3538ffc9eb576a1dae48ad671aa029adda9851def1b2e5`. The official image's installed package tuple is `@atproto/pds@0.5.51`, `@atproto/oauth-provider@0.25.1`, `@atproto/oauth-provider-ui@0.11.0`. The builder checks these inputs before installing dependencies.

The Dockerfile builds only the UI and its supporting TypeScript projects with Node 26.12.1 and pnpm 11.11.0, using the frozen upstream lock and disabled install scripts. A scratch stage exports only the completed `dist`; the final stage replaces exactly the installed UI directory in the official image. The verifier compares the complete runtime Config and every effective filesystem entry outside that directory against the official base.

Upstream's pinned `rolldown-plugin-bundle-manifest` hashes intermediate chunks in `generateBundle`; six native manifest hashes do not match the final Vite output. After Vite succeeds, this recipe recomputes each manifest item's `sha256` from its final named file, preserves every other field and asset byte, and writes deterministic two-space JSON. The provider continues to consume its native manifest format. Source evidence: `packages/internal/rolldown-plugin-bundle-manifest/src/index.ts` and `packages/oauth/oauth-provider/src/router/assets/assets-manifest.ts` at the locked revision; see the [checker contract](../../scripts/ci/pds-ui/README.md) for the observed Vite 8.3.1 behavior.

## Theme (P2.24x, P2.24z)

Before the source is hashed, the recipe appends the one theme, [`shared/ui/theme.css`](../../shared/ui/theme.css), and then [`ui/unset-theme.css`](ui/unset-theme.css) to upstream's `packages/oauth/oauth-provider-ui/src/style.css`, so Tailwind and Vite bundle both into the same hashed stylesheet. Upstream is stock shadcn on Tailwind 4 with the same variable names as the web app, so the theme sets its colours, radius and font names, and a theme change reaches the app and these screens together. `ui/unset-theme.css` adds only the fonts' edge path (`/_unset/fonts/`), the app's radius scale and the page ground, and holds no colour (`ui/theme.test.ts`). No component, route, form or script changes; buttons are upstream's stock ones, as the app's are. To read the theme, the recipe is `pds.Dockerfile` and builds from the repository root, as every `<name>.Dockerfile` does.

To look at a change without Docker, upstream's mock pages run with no PDS: in an `atproto` checkout at the locked revision, append the two files to that `src/style.css` and run `pnpm dev:ui` in `packages/oauth/oauth-provider-ui` (upstream README, "Running the mock").

This recipe builds the first-party image `ghcr.io/undefined6799/unset/pds`. `deployment/images.lock.json` pins its digest with `origin: first-party` and `verify: cosign-keyless`, and `deployment/compose.dev.yaml` runs that ref. `deployment/compose.dev.test.ts` requires the lock entry, that compose image and a local build of this recipe. `deployment/compose.local.yaml` and `deployment/compose.dev.source.yaml` build `pds.Dockerfile` from the repository root. On a push to `main`, `.github/workflows/publish-images.yml` builds it, pushes it by digest, scans it, signs it and attests it. The official `ghcr.io/bluesky-social/pds` image is only the final stage's base. Production deployment stays Alex's call (ADR 0027).
