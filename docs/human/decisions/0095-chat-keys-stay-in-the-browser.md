# 0095 — Chat keys stay in the browser: a generated recovery key saved at signup, expiry locks, Log out wipes

Record: Accepted by Alex 2026-11-20/21 in the chat planning thread (P6.00, minimal chat build). His decisions there,
as recorded in the chat architecture plan's Decisions section (paraphrased, not his words): only Log out wipes, and
expiry keeps the keys locked (2026-11-20); protecting messages is a required signup step (2026-11-20); the recovery
key is generated, never chosen, and saving it is the one thing signup asks (2026-11-21); on a shared browser the first
account's chat stays locked when another account signs in (2026-11-20). The SDK calls below are how the build plan
carries those decisions out.

## Context
PLAN §5.6 allows "later" for the recovery key at signup (decision 32 notes, 2026-10-03) and has every sign-out of the
app end that browser's chat device and wipe its local stores. The chat architecture plan of 2026-11-20 found that
keeping the device on expiry is sound if Log out also deletes the storage lock key on the server, so a browser that
never comes back holds only unreadable data. The minimal build has one unlock method, the recovery key; passkeys,
approve from another browser and several unlock methods on one vault come later (security pass finding 7: the SDK
does not keep a secret wrapped for several keys by itself).

What the pinned SDK does (matrix-js-sdk 43.0.0, `lib/crypto-api/index.d.ts`, `lib/crypto-api/recovery-key.d.ts`,
`lib/client.d.ts`, `lib/client.js`), read 2026-11-21:
- `createRecoveryKeyFromPassphrase()` with no argument makes a random key and its printable form; `decodeRecoveryKey`
  reads it back. `bootstrapCrossSigning` and `bootstrapSecretStorage({ setupNewSecretStorage, setupNewKeyBackup })`
  create the account's signing keys, the vault under that key, and the key backup (tested 2026-11-20).
- `initRustCrypto({ storageKey })` takes a 32-byte key that encrypts the local key store (tested).
- `CryptoEvent.KeyBackupSessionsRemaining` reports how many keys are still to be backed up.
- `clearStores()` deletes the sync store and both of the Rust crypto store's IndexedDB databases, named from
  `cryptoDatabasePrefix` (`lib/client.js`, lines 702 to 724). That answers the build plan's unverified item 3 from
  the source, on condition that the same prefix is passed; build step 11 tests it.

## Decision
1. **Our servers never hold a key that can read a message.** Message keys live in the browser; Synapse holds only the
   encrypted key backup and the encrypted vault. The client keeps `OnlySignedDevicesIsolationMode` (decision 13).
2. **The recovery key is generated by the SDK and saving it is a required signup step.** The "Save your recovery key"
   page runs `createRecoveryKeyFromPassphrase()`, `bootstrapCrossSigning`, then `bootstrapSecretStorage` with both
   flags set, and says "done" only once `isSecretStorageReady()` and `getActiveSessionBackupVersion()` confirm it.
   The key is shown in a field a password manager offers to save, with a Download button and a check of its last
   characters. The door lets exactly one browser run this setup for an account (security pass finding 14). Someone
   who leaves half-way is asked again, and stopped with "save your key first" before Log out.
3. **A new browser unlocks with that key:** `decodeRecoveryKey`, the `getSecretStorageKey` callback,
   `bootstrapCrossSigning({})`, `loadSessionBackupPrivateKeyFromSecretStorage()`, `checkKeyBackupAndEnable()`. A
   wrong key fails and the page asks again.
4. **Expiry locks.** Each browser's local key store is opened with a 32-byte storage lock key that the door makes,
   keeps sealed (ADR 0093) and hands back only after a ticket sign-in for the same account and device. Sync data stays
   in the SDK's default in-memory store, so no readable room list is left on disk. When the token runs out nothing is
   wiped; the next sign-in mints on the same device ID and gets the same lock key, with no unlock. Stores are kept per
   account (`cryptoDatabasePrefix`), so another account signing in on the same browser leaves the first one locked.
5. **Log out wipes.** The chat page waits for `KeyBackupSessionsRemaining` to reach 0, with a short deadline, then
   calls `stopClient()` and `clearStores()` with that account's prefix. The door asks `chat-admin` to revoke the
   session, which removes the device and its pusher, and deletes the lock key. Log out on unset.sh ends chat on the
   browsers that web session signed in the same way, through a queued job; a chat page opened later finds no lock key
   and wipes what is left.

## Alternatives
- **Wipe on every expiry, as PLAN §5.6 said.** Each expiry would mean typing the recovery key again. Declined by Alex.
- **Keep the recovery key optional at signup ("later").** Leaves new members with keys nobody can recover. Declined by
  Alex.
- **Keep a copy of users' keys on our servers to ease recovery.** Breaks the promise that our servers cannot read
  messages. Rejected.

## Consequences
- Supersedes PLAN §5.6's "later" allowed at signup and "signing out of the app ... wipes its local stores" for expiry;
  the step book's P6.08 and P6.16 change to match. P6.17's MAS consent step goes (ADR 0093).
- A browser that expired and never comes back holds an encrypted store; after Log out or erasure its lock key no
  longer exists, so the store cannot be opened.
- Keys not yet backed up when a session is ended without Log out (erasure, a revoked grant) are lost, as accepted in
  PLAN §5.6 on 2026-10-19.
- The lock key is personal data in the door's schema, deleted at Log out and by `eraseDid`.

## Compliance
- Build step 8: the signup page does not finish before both checks pass; a second browser trying setup is refused;
  a wrong key is refused and the page asks again.
- Build step 11: tests that expiry leaves the store locked and reopens it with no unlock, that Log out leaves no
  IndexedDB database of that account and no lock key, and that a second account on the same browser cannot open the
  first one's store.

## Notes appended after acceptance
- **2026-11-21, decision 5 as built:** no Log out on the chat page; unset.sh logout drives it (Alex, 2026-11-21); new
  door route POST /sign-out/redeem. POST /logout ends the web session and queues the chat devices it signed in; when
  it queued one, this browser holds it, and the tab goes through GET /logout/chat to `/sign-out/return#ticket=…` with
  a ticket for the ended session. The door spends it only on the entry this browser already holds (no new device, no
  renewal), the page takes the tab lock over and runs Log out as above, then returns to unset.sh through GET
  /logout/done, a stateless page whose meta refresh is a same-site navigation to /signed-out, so the issuer cookie
  stays Strict (RFC 6265bis-22 section 5.2). The queued end fires after 120 s if the page never finishes. The ticket's
  session must be the one that last signed the entry in (migration 0051), so it cannot log out another browser of the
  same member. Sign out everywhere queues every device at once and runs the same hop for the browser that pressed it,
  whose devices wait the 120 s instead (migration 0052); a revoked grant has no browser and only queues.
