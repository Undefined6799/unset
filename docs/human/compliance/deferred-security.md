# Deferred security items

Security gaps Alex has accepted for now, each with the fix we know and what it waits for. Alex asked for one list
(2026-11-23) so that when it is time, we know what to secure. Add a row when a record accepts a risk for later;
remove it only when a later record closes it, and name that record.

Alex expects Unset's 2FA security layer to be the next thing built after chat (2026-11-23), with everything
sensitive going behind it.

| # | What | Why deferred | Known fix | Source record | Waits for |
|---|---|---|---|---|---|
| 1 | Any signed-in session of a member, even one that never entered the recovery key, can replace or delete their chat offline device. It can destroy the messages waiting for them, keep a device reading their new messages after it signs out, and knock out another of their browsers by naming its device id. | Alex: "just keep it and record the risk" (2026-11-23). The fix needs a new hop and network path in front of Synapse. | Alex's idea (2026-11-23): since we control the Matrix server, it refuses deleting the offline device. That alone does not close it: a `PUT` also replaces the old one, and the member's own browsers must keep replacing it (the SDK renews it weekly and at every unlock). So a replace is accepted only when the new device is flagged dehydrated, signed by the member's own self-signing key (verified) and its id is its own curve25519 key. | [ADR 0114](../decisions/0114-chat-offline-device-risk-recorded.md), amending [ADR 0113](../decisions/0113-chat-keeps-elements-offline-device.md) | Unset's 2FA layer, or a decision to build the check first |
| 2 | A browser signed in through unset.sh that has not entered the recovery key still gets the keys for every new chat message, so a stolen unset.sh session reads new messages. Anyone who can create a device (chat-admin, MAS, web's ticket key) can too, and the sender sees no warning. | Accepted by Alex, not an open gap. 2026-11-21: "we can implement our own security on top"; 2026-11-23: reading new messages there is "part of the game", since the recovery key protects old messages. It stays on the list only as something the 2FA layer will tighten. | A second factor that proves a new device, or a browser's chat sign-in, before the device counts. | [ADR 0106](../decisions/0106-chat-device-trust-kept-and-what-it-gives-up.md) decision 2, amending [ADR 0104](../decisions/0104-chat-trusts-devices-as-element-does.md) | Unset's 2FA layer, with its own record |
| 3 | There is no way to reset a lost recovery key. A member who loses it cannot unlock chat history in a new browser, and an account whose setup was left half done can only be finished in that browser. | Reset is out of scope for this version. | A reset behind a step-up (a PIN or an emailed code, never the PDS password). It must also replace the offline device, since the old one's key sits in the vault the reset discards. | [ADR 0093](../decisions/0093-chat-sign-in-minted-by-our-servers.md) ("Deferred to later records"), [ADR 0100](../decisions/0100-one-browser-runs-recovery-key-setup.md) Consequences | Unset's 2FA layer, with its own record |
| 4 | Sensitive actions need no second check: deleting sign-in history, deleting chat history, changing notifications, deleting the chat offline device. Any signed-in browser may do them. | Alex (2026-11-21, 2026-11-23): the 2FA layer will gate them when it is built. | Require the second factor for each of these actions. | [ADR 0082](../decisions/0082-sign-in-history.md) (sign-in history); for chat history and notifications, Alex in the project chat on 2026-11-21, with no record yet; [ADR 0114](../decisions/0114-chat-offline-device-risk-recorded.md) decision 4 | Unset's 2FA layer, with its own record |
| 5 | The recovery key is typed inside the chat box, a frame on unset.sh with no address bar. unset.sh's page cannot read what is typed there. But a bad script on unset.sh could draw a look-alike box and ask for the key, and the member could not tell the difference. | Kept for staging testing (coordinator's recommendation, 2026-11-23, after Alex's "the recovery key only once"; Alex did not object). The chat box review (finding D2) agrees for staging. | Move key entry to a small top-level unset.cc pop-up, which needs unset.sh's COOP relaxed to `same-origin-allow-popups`, or have Alex accept it in a record. | [ADR 0115](../decisions/0115-chat-box-inside-unset-sh.md) Consequences; chat box review D2 | Before production |
| 6 | Messages sent from a browser that never had the recovery key typed in cannot be read by any later browser of the member. Such a browser cannot upload its message keys to the key backup, since it neither trusts the backup nor holds its key (matrix-js-sdk 43.0.0 `src/rust-crypto/backup.ts:351-358`). Found on staging (Alex's list, 2026-11-23, item 1). | Alex (2026-11-23): not now; he will deal with it with Better Auth, around the move to the organization repository. It follows from row 2's choice that such a browser chats without the key, and "Skip for now" on the unlock card (Alex, 2026-11-23: chat stays usable without the key) makes such browsers more common. | Ask for the recovery key once on each browser before it sends, as Element does; or Unset's 2FA layer proving the device. | [ADR 0106](../decisions/0106-chat-device-trust-kept-and-what-it-gives-up.md) decision 2 | Around the move to the organization repository |
